# NAS TLS delivery

This component obtains `nas.bohdal.name` through the existing production DNS-01 `ClusterIssuer`, then stages a pinned, in-place certificate delivery path to DSM at `10.1.100.10:5001`. DNS-01 may create temporary ACME TXT records while cert-manager proves control of the domain; this component creates no permanent application DNS record, Service, Ingress, LoadBalancer VIP, DHCP lease, gateway rule, or Kubernetes API credential.

The `nas-tls-issue`, `nas-tls-bootstrap`, `nas-tls-delivery`, and `observability-nas-tls` Flux children are all suspended when introduced. Enable them independently only after the relevant gate is recorded: issue the source certificate first, establish the first DSM import through an independently trusted operator channel, pin the existing DSM certificate id in `reconciler-config.json`, and then enable the one-shot bootstrap, recurring delivery, and monitoring stages in that order. The reconciler always uses strict system-trust TLS with SNI and hostname `nas.bohdal.name`; it has no HTTP, expiry-ignore, fingerprint-only, or insecure fallback.

The operator-approved DSM auth contract is Bitwarden project `sk-home`, item key `NAS_TLS_DSM_AUTH`, and an actual item ID supplied as non-secret operator metadata. The item value must be exactly a JSON object with bounded, non-empty `username` and `password` strings. From the repository devcontainer, run the helper's default read-only preflight with the independently verified `nas-tls` namespace UID:

```sh
python3 scripts/nas-tls-bootstrap.py \
  --kubeconfig /path/to/sk-talos-kubeconfig \
  --namespace-uid '<independently verified nas-tls namespace UID>' \
  --bitwarden-item-id '<actual operator-approved Bitwarden item ID>'
```

The helper validates the trusted project and exact item metadata, writes an isolated non-secret BWS configuration with `state_opt_out = "true"`, captures both subprocess streams with a timeout, and passes no `BWS_*` settings to Kubernetes. It verifies the namespace UID and required restricted Pod Security labels, then checks an existing Secret's exact name, namespace, labels, `Opaque` type, `username`/`password` data, and lack of owner references. It emits fixed diagnostics and never writes credentials to a file, log, or argument list.

After explicit production approval and a successful preflight, repeat the same command with `--apply-secret`. The helper uses an atomic `kubectl create -f -` only when `nas-tls-dsm-auth` is absent, then reads the object back and compares the exact contract; a concurrent creator, drift, adoption, overwrite, or rotation fails closed. The source Secret `nas-tls` remains owned by cert-manager. The DSM principal must have the administrator-class certificate-import permission required by the DSM API; this repository does not claim a narrower privilege is sufficient. Do not execute the apply mode until the production gate and trusted DSM channel are recorded.

The `issue/reconciler-config.json` file is the reviewed runtime contract: hostname and port stay fixed to `nas.bohdal.name:5001`, source and auth paths stay mounted paths, `target_description` identifies the existing DSM slot, and `target_id` must remain `activation-required` until the independently trusted bootstrap records the exact stable DSM id. `minimum_lifetime_seconds`, `timeout_seconds`, response/upload bounds, and `retry_count`/`retry_delay_seconds` are safety limits; the current values require fourteen days of source certificate lifetime and perform one import followed by at most four post-import read-back attempts with a five-second delay.

The delivery CronJob runs once daily at 02:17 in the Kubernetes controller's timezone, forbids overlap, accepts a start up to 30 minutes late, and gives each Job five minutes with no Kubernetes-level retry; the reconciler's bounded attempts stay inside that one run. Bootstrap uses the same five-minute, no-retry Job limits. A failed Job remains available under the manifest's history and TTL settings; inspect its sanitized result and DSM inventory before a reviewed rerun.

The reconciler validates the projected cert/key pair with `SSLContext.load_cert_chain`, performs a bounded loopback full-chain handshake using system trust and the canonical hostname, checks peer-decoded dates and remaining lifetime, and captures one immutable Secret projection before upload. DSM discovery is constrained to the reviewed API paths and versions. The selected certificate must have exactly one matching description and the operator-pinned stable id. Import preserves the id, description, `is_default`, and complete service assignment list; provider-shaped service objects use the composite `(owner, service, isPkg)` identity with deterministic ordering while retaining `display_name` and every other returned binding field. A changed binding, duplicate target or composite binding, unknown response shape, redirect, upload failure, or post-import served-leaf mismatch fails closed. Session material is kept in memory and sent only through the DSM cookie/header contract; public API selectors may appear in the URL, never passwords, SIDs, or SynoTokens.

The bootstrap child is a separately approved one-shot run of the same strict reconciler. The existing expired or wrong-name DSM certificate cannot satisfy its TLS precondition; use an independently trusted operator channel to repair that precondition before enabling the child, then record the exact existing DSM stable id in the reviewed ConfigMap. The current staged repository has not performed that live preflight or claimed activation acceptance.

Before production activation, record all fresh read-only gates in the review: the cert-manager source Secret is Ready and valid; a readable sanitized RouterOS inventory artifact was produced from current `main` (the earlier MCP artifact reference returned HTTP 403, so no baseline bytes are claimed); and an actual NAS pod path can reach `nas.bohdal.name:5001` over TCP and complete strict system-trust TLS with the canonical SNI. The expired, wrong-name live NAS certificate still authorizes no DSM login or import. No permanent application DNS, DHCP, BGP, VIP, or other routing change is part of this component. If preflight proves that the existing pod-to-NAS route is missing, repair it only through its own targeted, reviewed immutable gateway plan and production gate; do not fold that change into NAS TLS. Keep all four Flux children suspended, keep `target_id` at `activation-required`, and keep runtime trust on the system CA store until every gate and the explicit production approval exist.

Rollback is a GitOps sequence because suspending a Flux Kustomization does not stop a live CronJob, Job, or policy. First commit `spec.suspend: true` in `kubernetes/flux/infrastructure/nas-tls/delivery/cronjob.yaml` and leave `nas-tls-delivery` unsuspended until Flux reports that the CronJob is suspended. Inspect any bounded in-flight bootstrap or delivery import and its sanitized result before choosing to let it finish. If the bootstrap Job must terminate, remove that Job from the active bootstrap child so Flux prunes it; if a generated delivery Job must terminate, remove the CronJob from the active delivery child so Kubernetes garbage collection removes its owned Jobs and Pods. Verify the actual Jobs and Pods are gone before suspending the relevant Flux child. Deleting the Kubernetes auth Secret alone does not revoke a DSM SID or bytes already mounted in a running Pod, so it is never treated as workload termination or credential revocation. A failed post-import Job requires investigation and a fresh reviewed run; it is never hidden by an automatic retry, rollback, or service rebind.

Reconcile a separate rollback commit that removes or reverts `vm-static-scrape.yaml`, `vm-rules.yaml`, and `network-policy.yaml` from the monitoring tree while `observability-nas-tls` remains active, then wait for those objects to be removed before suspending the monitoring Kustomization. Only after active credentialed workloads and monitoring egress are handled may the bootstrap, delivery, or monitoring Flux children be suspended. Preserve the `nas-tls` Namespace, cert-manager source Secret, selected DSM certificate slot, and every service binding throughout rollback; do not perform ad-hoc live mutations.

The monitoring child adds a strict HTTPS blackbox probe for the unauthenticated DSM API-info path, an additive Cilium rule for only `10.1.100.10/32:5001`, served-leaf expiry alerts, readiness and missing-probe alerts, and KSM-based CronJob failure/last-success staleness alerts. It remains independently suspended until delivery is intentionally activated.

Run `mise run nas-tls-check` from the repository devcontainer before review; it runs offline reconciler tests, create-only Secret bootstrap tests, native VMRule syntax and semantic tests, and renders the issue, bootstrap, delivery, and monitoring Kustomize trees without credentials or live cluster access. Use `mise run nas-tls-alerts-check` for a monitoring-only rule change.

The API path and session handling are based on the [official Synology WebAPI guide](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Package/Calendar/All/enu/Calendar_API_Guide_enu.pdf), the maintained [Synology certificate provider implementation](https://github.com/batonogov/terraform-provider-synology-dsm/blob/main/internal/client/certificate.go), and the maintained [acme.sh DSM deploy hook](https://github.com/acmesh-official/acme.sh/blob/master/deploy/synology_dsm.sh). The provider's state boundary is unsuitable here because it retains private keys in state; this narrow mounted-Secret reconciler is the explicitly documented exception and must not be mixed with provider ownership.
